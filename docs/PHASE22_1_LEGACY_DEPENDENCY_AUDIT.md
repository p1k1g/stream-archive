# Phase 22.1 — Legacy Web / Dependency Audit & Cutover Plan

## Audit baseline

Phase 22.1 is an audit/cutover-planning phase only. It does **not** remove the Web UI, Axum server, launcher, `RUN_WEB.bat`, provider runtime, shared core, or packaging entries.

Baseline inspected:

- Phase 21.9 PR #88 is merged.
- Phase 21.9 merge commit on `main`: `bd424df1812cbe941aa58a31a6b75038d5b02194`.
- Last Phase 21.9 PR CI baseline: workflow run #721, successful on Windows/Linux/macOS plus Windows portable checks.
- Audit branch: `phase22-1-legacy-audit`, created from current `main`.
- There is no repository-root Cargo workspace manifest. `rust-web/Cargo.toml` and `rust-gui/Cargo.toml` are separate manifests; the GUI depends on the `rust-web` package as the `stream-archive-server` Rust library.

The name `rust-web` is historical/packaging-oriented. It currently contains both reusable application/runtime code and the Web presentation. It must not be deleted as a unit.

## Current architecture

The current product has four distinct presentation/entry layers over a partly shared Rust runtime:

```text
Windows Native
StreamArchive.exe
  -> rust-gui/src/main.rs
  -> rust-gui/src/controller.rs
  -> stream_archive_server::app_core::StreamArchiveCore
       -> Store / settings / security
       -> NativeWatcherManager / RecorderManager
       -> common VOD manager + SOOP/CHZZK providers
       -> Queue service / History service
       -> BackupManager / Storage service / Diagnostics
       -> platform_runtime process ownership

Unix/headless CLI
stream-archive-cli
  -> tool discovery + direct settings DB helper commands
  -> "serve" currently launches stream-archive-server as a child
       -> current Axum/server runtime

Web compatibility
RUN_WEB.bat
  -> stream-archive-launcher.exe
  -> stream-archive-server.exe
  -> Axum routes + browser HTML/CSS/JS
  -> server-local AppState
       -> the same lower-level Store / watcher / VOD / queue / backup modules

Direct Web troubleshooting
RUN_SERVER_CONSOLE.bat
  -> stream-archive-server.exe
```

The most important architectural finding is that **Native does not require the Web server**. The Slint controller resolves the backend and opens `StreamArchiveCore` directly. It does not call localhost HTTP.

A second important finding is that the Web server does **not yet use `StreamArchiveCore` as its bootstrap**. `rust-web/src/main.rs` privately declares many of the same modules and assembles its own server `AppState`. This makes some shared source files compile twice: once through `src/lib.rs` for Native/shared consumers and again through the server binary's private module tree. Several current dead-code warnings are artifacts of that duplicate compilation, not proof that the underlying shared APIs are unused.

### Launcher answers

1. Native default execution does **not** use the launcher.
2. CLI/headless does **not** use the launcher.
3. The launcher is a Windows-only Web fallback bootstrap: probe loopback, start `stream-archive-server.exe`, wait for the server, then open the browser.
4. Removing the launcher requires no Native replacement. The only lost behavior is the convenient Web-server/browser bootstrap.
5. No unique shared backend-resolution or media-runtime logic was found in the launcher. Its executable-directory lookup is local to locating the sibling server.

Therefore the launcher is a clean Phase 22.3 removal candidate **if the Web fallback is retired**.

## Native dependency graph

### Native bootstrap

```text
rust-gui/src/main.rs
  -> controller::bind
  -> backend::resolve_backend_dir
  -> StreamArchiveCore::open
  -> Store::default_path / migrate_legacy_database / Store::open
  -> StreamArchiveCore::assemble
```

The controller starts the long-lived shared services through the Core:

- `spawn_vod_history_sync`
- `spawn_queue_worker`
- `spawn_auto_backup`

Shutdown is also routed through `core.shutdown()`.

### LIVE watcher / recording

```text
Slint LIVE actions
  -> controller Request
  -> StreamArchiveCore watcher facade
  -> NativeWatcherManager
  -> platform-neutral LiveSession/provider dispatch
  -> SOOP or CHZZK LIVE provider
  -> RecorderManager
  -> Streamlink / FFmpeg
  -> platform_runtime::spawn_owned
  -> Windows Job Object / Unix process group
```

### VOD

```text
Slint VOD
  -> controller
  -> StreamArchiveCore::{analyze_vod,download_vod,cancel_vod}
  -> common vod::VodManager
  -> platform detection
  -> platform/soop/vod.rs or platform/chzzk/vod.rs
  -> yt-dlp / Streamlink / FFmpeg
  -> retained process ownership
```

### Queue

```text
Slint Queue
  -> controller
  -> StreamArchiveCore queue methods
  -> queue_service::VodQueueManager
  -> common VodManager
  -> provider VOD implementation
  -> canonical SQLite queue state
```

### History

```text
Slint History
  -> controller
  -> StreamArchiveCore::history
  -> history_service::load_history
  -> canonical SQLite
  -> rust-gui/history_adapter.rs presentation
```

### Settings / secrets / providers

```text
Slint Settings
  -> controller
  -> StreamArchiveCore environment/provider update methods
  -> environment_settings / primary_config
  -> Store
  -> security boundary for secret persistence
```

Provider network/auth behavior remains below `platform/*`. The GUI does not call providers directly.

### Storage

```text
Slint LIVE storage card
  -> controller
  -> StreamArchiveCore::storage_snapshot
  -> storage_service
  -> canonical settings/channels + filesystem probe
  -> rust-gui/storage_adapter.rs
```

### Backup / restore / diagnostics / logs

```text
Settings > Manage
  -> controller
  -> StreamArchiveCore
       -> BackupManager
       -> diagnostics
       -> bounded LogBuffer
       -> canonical Store
```

Restore safety checks are shared-Core behavior: Watcher, active VOD, and Queue activity are checked before restore.

### Native picker

`rust-gui/src/native_picker.rs` is a GUI-only platform boundary. On Windows it delegates to the native picker implementation in the GUI crate. It does not require the old Web `/api/local-picker` route.

### Native bypass audit

Current Architecture guards and source inspection agree:

- no localhost HTTP from `rust-gui/src`;
- no Axum dependency in the GUI controller;
- no direct `rusqlite` access from `rust-gui/src`;
- no direct `Command::new`/process ownership from `rust-gui/src`;
- process ownership remains in shared runtime/provider code;
- `StreamArchiveCore` itself is kept free of Axum/HTTP presentation types.

### Duplicate-module issue

Three Web adapter patterns are notable:

- `vod_queue.rs` loads `queue_service.rs` again with `#[path = "queue_service.rs"] mod shared_queue;`
- `history_storage.rs` loads `history_service.rs` again with `#[path = "history_service.rs"] mod shared_history;`
- `main.rs` declares many shared source files as private modules while `lib.rs` also exports them.

This duplication is a major source of misleading `dead_code` warnings. Phase 22.2 should remove genuine dead APIs first and, where safe, reduce duplicate compilation rather than suppress warnings.

## Compiler warning inventory

Source: successful Phase 21.9 CI run #721. The inventory intentionally separates compiler dead-code warnings from Clippy advisory warnings and Node/dependency warnings.

### A. Process-runtime compatibility warnings

Common:

- `platform_runtime.rs: OwnedProcessTree::capture`
- `terminate_owned`
- `terminate_owned_checked`

Windows-only compatibility subtree additionally reports unused identity/snapshot helpers, including:

- `terminate_windows_tree`
- `ERROR_ACCESS_DENIED`, `ERROR_INVALID_PARAMETER`
- FILETIME conversion constants/helpers
- `ProcessIdentity`, `ProcessSnapshot`
- `child_identity`, `open_identity`, `query_identity`
- snapshot identity guards
- `OwnedTreeJob::capture_running_child`
- `absorb_preexisting_descendants`
- `process_snapshot`, `process_tree_pids`, `child_pid_is_current`

Unix reports the corresponding compatibility helpers:

- `capture_running_child`
- `process_group`
- `posix_getpgid`

Classification: **COMPATIBILITY / TEST-ADJACENT, not blindly DEAD**. Production media paths use retained `spawn_owned`. Some compatibility functions are referenced only by tests and old fallback paths. Phase 22.2 should shrink or test-gate these carefully while preserving Job Object/process-group regression coverage.

### B. Warnings caused by server duplicate module compilation

The server binary's private module tree reports APIs as unused even though the library/Native path uses them:

- `BackupManager::update_policy` — used by `StreamArchiveCore::update_backup_policy`; KEEP.
- History local timestamp formatter/sort key — used by Native adapters; KEEP.
- `storage_service::format_bytes_compact` — used by Native storage adapter/controller; KEEP.
- `Store::is_first_run_unconfigured` — used by Native Core/controller; KEEP.
- `VodQueueManager::shutdown` — used by `StreamArchiveCore::shutdown`; KEEP.

Classification: **SHARED API + duplicate compilation warning**. Fix architecture/target compilation rather than deleting these functions.

### C. Likely genuine dead APIs

- `BackupManager::list`: no source caller found; `snapshot()` uses `list_locked()`.
- `security::is_protected`: no source caller found.
- `atomic-write-file` direct Cargo dependency: no source reference found.

Classification: **DEAD-CANDIDATE**. These are the best first Phase 22.2 removals after a fresh search/test pass.

### D. Clippy advisory inventory

The current workflow runs Clippy advisory-only, so these do not fail CI. Current source warnings include:

- `collapsible_if` across backend/backup/history/watcher/queue/recorder/providers/store/CLI;
- `needless_return`;
- `new_without_default` for `LogBuffer`;
- `field_reassign_with_default` in tests/models;
- `too_many_arguments` in watcher and SOOP/CHZZK VOD helpers;
- `suspicious_open_options` on CHZZK files opened with `create` without explicit truncate behavior;
- `bool_assert_comparison` in security tests;
- explicit auto-deref;
- auth `manual_is_multiple_of` / constant-size `chunks_exact` suggestions.

Phase 22.2 should prioritize semantic/dead-code warnings and suspicious file-open semantics before cosmetic lint rewrites.

### E. Non-project warning

Actions Node runtime emits a `punycode` deprecation warning. This is dependency/tooling noise, not Stream Archive Rust source.

### Warning-zero scope proposal

For Phase 22.2:

1. Target **zero Rust compiler dead-code/unused warnings in Stream Archive production targets**.
2. Keep Clippy advisory initially; clean safe mechanical lints separately.
3. Do not suppress with broad `#[allow(dead_code)]` / `#[allow(unused)]`.
4. Do not count third-party/tooling warnings such as Node `punycode` against the source warning-zero goal.

## Risks

1. **Misclassifying rust-web as Web-only.** The Native GUI depends on its library.
2. **Compiler-warning false positives from duplicate module trees.** Deleting Native-used APIs based on server-bin warnings would break the GUI.
3. **CLI runtime dependency.** Removing `stream-archive-server` today breaks `stream-archive-cli serve`.
4. **Process ownership regression.** Cleanup of compatibility helpers can accidentally weaken exact Job Object/process-group semantics.
5. **Restore/auth difference.** Web restore invalidates browser sessions; Native restore does not need browser-session logic. Removing `backup.rs` is safe only after deciding Web support, not by modifying `BackupManager`.
6. **Remote capability loss.** Removing browser auth/SSE/reverse proxy removes remote management, not just old styling.
7. **Packaging assumptions.** CI and ReleaseSafety currently require Web compatibility artifacts; cleanup must update checks intentionally.
8. **Web management token persistence.** `BUILD_PORTABLE.bat` preserves `backend\.stream-archive`; this should not be removed until Web token use is gone.
9. **CHZZK destination safety.** Claim/finalizing behavior is shared runtime and unrelated to Web cleanup.

## Recommended removal order

### Phase 22.2 — Dead Code / Compiler Warning Cleanup

1. Re-run search + `cargo check`/Clippy baseline.
2. Remove unambiguous dead API/dependency:
   - `BackupManager::list`;
   - `security::is_protected`;
   - `atomic-write-file` if still unreferenced.
3. Separate **duplicate-module warnings** from real dead code. Do not remove Native-used Core APIs.
4. Reduce/test-gate obsolete process compatibility wrappers only while preserving exact ownership tests.
5. Fix safe compiler/Clippy issues:
   - suspicious OpenOptions semantics first;
   - unused/dead warnings;
   - mechanical collapsible-if/needless-return/test lint cleanup.
6. Goal: zero project compiler dead-code/unused warnings for production targets; Clippy can be tightened after semantic cleanup.

### Product decision before broad 22.3 removal

Choose one:

- **Retire remote/browser management:** proceed with full Web presentation + auth/session/SSE/launcher cleanup.
- **Keep remote browser management:** keep or extract Web presentation as an explicit optional compatibility feature; do not pretend it is dead.
- **Undecided:** launcher/browser files remain compatibility code.

### Phase 22.3 — Legacy Web Presentation / Launcher Removal

If Web is retired:

1. Remove launcher + `RUN_WEB.bat` generation and launcher package checks.
2. Remove browser static assets and Web-only picker/SSE/auth presentation.
3. Remove Web-specific Axum adapter modules while preserving shared services.
4. Rewrite `Architecture.ps1` and `Providers.ps1` to drop browser DOM/JS assertions but keep provider/Core invariants.
5. Rewrite `ReleaseSafety.ps1`, check workflow, release workflow, docs and package verification.
6. Remove Web-only dependencies (`tokio-stream`, `tower-http`, and eventually `axum`/`tracing*` when no server remains).
7. Drop launcher-only Windows UI feature flags.
8. Stop preserving Web management-token state once no Web server consumes it.

### CLI/headless prerequisite to deleting the server executable

Before deleting `stream-archive-server.exe` entirely, change `stream-archive-cli serve` so it no longer launches the Web server. Preferred direction:

```text
stream-archive-cli serve
  -> shared StreamArchiveCore/headless runtime loop
  -> watcher/queue/backup lifecycle
  -> no browser/Axum requirement
```

This can be a bounded 22.3 sub-step or a dedicated cutover slice. Until then, the server remains a CLI runtime dependency even though Native does not need it.

## Direct answers

### Does Native execution actually need the Web server?

**No.** Native opens `StreamArchiveCore` directly and owns its own shared runtime lifecycle.

### How much of rust-web is shared core?

Most runtime modules exported by `src/lib.rs`: Core, Store, settings/config, providers, watcher, recorder, VOD, Queue, History, Backup, Storage, diagnostics, security, tool discovery and process ownership.

### Which Web code can be removed without affecting Native?

Browser static assets, Web auth/session/CSRF, SSE, Web local picker and Axum adapter modules can be removed from the Native dependency graph. They still affect Web/remote support, and the server entry must remain until the CLI `serve` dependency is addressed.

### Is the launcher still required?

**Not for Native or CLI.** It exists only for the Windows Web fallback.

### Is RUN_WEB.bat ready to be removed?

**Technically yes for local Native parity, but product-decision blocked.** Remove it only after deciding that browser/remote Web compatibility is no longer supported.

### What current warnings are truly dead?

The clearest current candidates are `BackupManager::list`, `security::is_protected`, and the unreferenced `atomic-write-file` dependency. Process-capture compatibility code is also unreferenced in production but is safety/test-adjacent and needs a deliberate test-preserving cleanup. Several other warnings are false positives caused by the server compiling shared source as private modules.

### What is safe to delete in Phase 22.2?

Only the unambiguous dead APIs/dependency and carefully isolated compatibility/test-only code. Do **not** delete Native-used Core APIs, shared services, providers, or process ownership code to silence server-bin warnings.
